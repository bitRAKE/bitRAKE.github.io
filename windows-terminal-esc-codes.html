Windows Terminal — Escape Sequence Reference

Every control sequence the Windows Terminal output engine recognizes, plus the reports it sends back — derived directly from the microsoft/terminal source. The code is the source of truth.

C0 controls ESC CSI DCS OSC

Filtering matches sequence names, byte patterns, and descriptions across every table.

Source of truth — read from these files

  • parser/OutputStateMachineEngine.hpp — the *ActionCodes enums define every recognized byte sequence (VTID("…")).
  • parser/OutputStateMachineEngine.cpp — ActionExecute / ActionEscDispatch / ActionVt52EscDispatch / ActionCsiDispatch / ActionDcsDispatch / ActionOscDispatch map each sequence to a dispatch call.
  • adapter/ITermDispatch.hpp — dispatch interface; signatures show each sequence's parameters.
  • adapter/DispatchTypes.hpp — the VTParameter default rules and the parameter-value enums (SGR, modes, erase, cursor style, status…).
  • adapter/adaptDispatch.cpp / adaptDispatchGraphics.cpp — the concrete handlers (and the report generators in §9).

⚠️ Do not trust Microsoft Learn as the spec. The official Console Virtual Terminal Sequences page not only lags the repo — it omits many sequences listed here (DCS, most rectangular-area ops, the Kitty keyboard protocol, the newer DEC private modes, several OSCs) — it also contains outright errors when checked against the code.

Where the doc and the source disagree, the source wins. This reference follows the source.

§0 Notation — read this first #

Everything in this document is built from one encoding. Every escape sequence begins with one of a small set of introducers, followed by optional parameters and intermediate bytes, and ends with a final byte that selects the command.

Introducers #

SymbolBytes7-bit formC1 (8-bit)Meaning
ESC0x1B——Escape — starts every sequence below
CSIESC [0x1B 0x5B0x9BControl Sequence Introducer
DCSESC P0x1B 0x500x90Device Control String
OSCESC ]0x1B 0x5D0x9DOperating System Command
STESC \0x1B 0x5C0x9CString Terminator (ends DCS/OSC; BEL 0x07 also accepted)
SP0x20——a literal space byte, used as an intermediate

The 8-bit C1 single-byte forms are accepted only when 8-bit C1 reception is enabled (see DECAC1 / S8C1T). Otherwise use the 7-bit ESC-prefixed forms shown throughout.

Anatomy of a CSI sequence #

CSI  ?      38 ; 5 ; 196        SP        m
└┬┘  └┬┘    └──────┬──────┘     └┬┘      └┬┘
intro private   parameters   intermediate final
     prefix    (';'-separated,            byte
               ':' for sub-params)
  • Parameters (Ps, Pn, Pl, Pc, …) are decimal numbers separated by ;. A parameter may be omitted (e.g. CSI ; 5 H), in which case its default applies.
  • Sub-parameters are separated by : within one parameter (used by SGR, e.g. 38:2:255:0:0).
  • Private/prefix bytes (? > = < !) and intermediate bytes (SP " $ ' * , # &) sit between the introducer/params and the final byte; they are part of what selects the command. A sequence written CSI ? Ps h means literally ESC [ ? <number> h.

Parameter-name conventions used in the tables #

TokenMeans
Psa single selective/numeric parameter
Pna numeric count or distance
Pl ; Pcline ; column
Pt;Pl;Pb;Prtop ; left ; bottom ; right (rectangle)
<F>a single final "designator" byte (e.g. a charset id)
…a data string, terminated by ST (for DCS/OSC)

Spaces shown between bytes in the tables are for readability only — do not send them, except where the token is literally SP (0x20). Tip: click any grey byte chip to copy its literal sequence (with ESC expanded to \x1b).

§0.1 How parameters & defaults work #

A numeric parameter is a VTParameter (DispatchTypes.hpp). The default is applied by the type the parameter is read as, right at the dispatch site (parameters.at(N)):

VTParameter() : _value{ -1 } {}                 // an OMITTED parameter is stored as -1
bool  has_value()      const { return _value >= 0; }
VTInt value()          const { return _value; }
VTInt value_or(d)      const { return _value < 0 ? d : _value; }     // omitted -> d
operator T()  /*enum*/ const { return static_cast<T>(value_or(0)); } // omitted -> 0
operator VTInt()       const { return _value <= 0 ? 1 : _value; }    // omitted OR 0 -> 1
Read asOmitted (-1)Explicit 0Rule
VTInt — numeric: counts, distances, positions11implicit operator VTInt()
enum — selective: erase type, mode, cursor style…00implicit operator T() → value_or(0)
value_or(0) explicitly — margins, rectangle coords00"0 = use the natural extent"

VTParameters::at(i) past the end returns an omitted parameter, and size() is always ≥ 1 (an empty list == one default parameter). Selective sequences (ED, EL, SM/RM, TBC…) use for_each, applying the action once per supplied parameter. Defaults shown in the tables are what the handler receives for an omitted parameter.

§9 Reports — what the terminal sends back #

Everything in §1–§8 is host → terminal (the app writing to the screen). This section is the opposite direction: the bytes the terminal writes onto the application's input stream in reply to a query. These are produced in the adapter (adaptDispatch.cpp), not the parser, by three helpers — so the wrapping is uniform:

_ReturnCsiResponse(body)  ->  CSI  body            // CSI = ESC[  or  0x9B
_ReturnDcsResponse(body)  ->  DCS  body  ST         // DCS = ESCP  or  0x90 ;  ST = ESC\ or 0x9C
_ReturnOscResponse(body)  ->  OSC  body  ST         // OSC = ESC]  or  0x9D ;  ST = ESC\ or 0x9C

8-bit nuance (verified). The introducer is chosen at send time from TerminalInput::Mode::SendC1. When the app has enabled 8-bit C1 transmission (via S8C1T, ESC SP G), responses use the single-byte C1 forms (CSI=0x9B, DCS=0x90, OSC=0x9D, ST=0x9C); otherwise the 7-bit forms (ESC [, ESC P, ESC ], ESC \). The bodies below are shown without the introducer/terminator. All numeric coordinates are 1-based (VT origin 1,1).

Under ConPTY, some of these are suppressed or forwarded rather than answered locally (e.g. the Kitty-keyboard query returns early when IsConPTY()), because the real terminal downstream is the authority.

9c · Mode report — DECRQM → DECRPM #

CSI Ps $ p (or CSI ? Ps $ p for private) replies CSI [?]Ps;Ps_state $ y, where the ? is present iff the mode is a DEC private mode, and Ps_state is:

0 not recognized · 1 set · 2 reset · 3 permanently set · 4 permanently reset.

The terminal queries live state for every mode listed in §8 (e.g. CSI ? 25 $ p → CSI ?25;1$y when the cursor is visible). Grapheme-cluster mode (2027) reports the permanent variants (3/4).

9d · DECRQSS — request a setting's value (DCS $ q <id> ST) #

The app sends DCS $ q followed by the final/intermediate bytes of the control it's asking about, then ST. A valid reply is DCS 1 $ r <value><id> ST; an invalid/unsupported request replies DCS 0 $ r ST.

Source caveat (from the code comment): WT uses 1=valid / 0=invalid, per DEC STD 070 — the opposite of what most DEC manuals state.

9h · OSC color & clipboard queries #

A ? in place of a color spec asks the terminal to report the current value, as 16-bit-per-channel rgb:RRRR/GGGG/BBBB (each 8-bit channel scaled ×0x0101).

RequestReply bodyReports
OSC 4 ; Pi ; ? STOSC 4;Pi;rgb:RRRR/GGGG/BBBB STPalette entry Pi. No reply if that entry is unset (INVALID_COLOR).
OSC 10/11/12/17 ; ? STOSC Ps;rgb:RRRR/GGGG/BBBB STDynamic resource (fg/bg/cursor/highlight). Ps echoes the request number. No reply if unset.
OSC 52 ; Pc ; ? ST(no reply)Clipboard read-back is parsed but intentionally not answered — the dispatch writes the clipboard only on a set (!queryClipboard); queries are dropped (privacy).

9i · Answerback & VT52 #

  • ENQ (0x05) → EnquireAnswerback() → _api.ReturnAnswerback(): sends the user-configured answerback string (content is host/settings-defined, not hard-coded here).
